Assistant

Yes — a slow or stalled network can absolutely cause your watchdog to fire. Your timing description (right when transmission starts, sometimes after one or two uploads) matches how the code is structured today.

Can slow network cause a watchdog timeout?

Yes. The AVR watchdog is 8 seconds. Anything that blocks the main loop longer than that without calling wdt_reset() can trigger it. Network code is a prime suspect:

  • client.connect() blocks until TCP succeeds or times out (DNS + SYN retries)
  • client.write() / client.flush() can block on a slow link
  • delay(EthStartupDelay) is a 5-second blind wait with no watchdog feed
  • getNtpTime() waits up to 1.5 seconds with no feed
  • Up to 5–6 uploadWeather() calls run back-to-back in a loop

Is watchdog feeding still missing during transmissions?

Partially fixed, but not enough. Compared to your fix/wdt_reset branch, the current code is missing some feeds that branch had.

What feeds the watchdog today:

LocationFed?
Once per second in loop()Yes
enableEthernet() start/endYes
delay(EthStartupDelay) (5 sec)No
Before/after client.connect()Yes
After client.write()No (was in fix/wdt_reset)
Inside while (client.available())No (was in fix/wdt_reset)
Between multiple uploadWeather() callsNo
getNtpTime() wait loopNo

The risky pattern is that the once-a-second wdt_reset() at the top of the second-tick runs once, then the upload block can run for many seconds without another feed.

And in uploadWeather(), only connect is bookended — write, flush, and the response read loop have no feeds.

So “after two transmissions” fits: first upload may finish within 8 seconds; the second connect() or a slow response read can push past the limit.

Can you increase the watchdog to 15 seconds?

No — not with the hardware watchdog on ATmega2560. The maximum is 8 seconds (WDTO_8S). Your enableWatchdog() already uses that max. 15 seconds would require a different approach (e.g. software timer), not a simple prescaler change.

Disable watchdog during transmissions?

Possible (wdt_disable() before upload, enableWatchdog() after), but not recommended as the first fix:

  • A hung client.connect() would never recover
  • You lose protection exactly when network code is most likely to wedge
  • Feeding during blocking calls is safer and keeps hang detection

Good ways to test this

  1. Serial timestamps — Log millis() before/after enableEthernet(), each uploadWeather(), connect, write, and flush.
  2. Induce slow/failed network at the 5-minute upload window: unplug Ethernet, block port 80, or point CSSserver at an unreachable IP (bench only).
  3. Watch EEPROM counters — eeWatchdogCounter and crash time on boot.
  4. Artificial delay (bench) — Add delay(10000) inside uploadWeather().
  5. Cherry-pick fix/wdt_reset — That branch added feeds after write and in the response-read loop; worth merging and extending.

Recommended fix (better than disable or 15s)

  1. Merge the fix/wdt_reset feeds (after write, in the read loop).
  2. Replace delay(EthStartupDelay) with a loop that calls wdt_reset() every second.
  3. Add wdt_reset() at the top of the upload for loop (between uploads).
  4. Add wdt_reset() in getNtpTime()'s wait loop.

That should cover slow networks without weakening watchdog protection. I can apply those changes on your current branch if you want.

ok, however, there was mention that the actual wd feeding function was nulled out somewhere in the ethernet library via a #define. is that true?

Assistant

Partly true — but it's yield(), not wdt_reset(), and on your Mega it's worse in a different way.

What the Ethernet library actually does

In Ethernet 2.0.2 (socket.cpp), there is this pattern:

#if ARDUINO >= 156 && !defined(ARDUINO_ARCH_PIC32)
extern void yield(void);
#else
#define yield()
#endif
PlatformWhat happens
Very old Arduino (< 1.5.6) or PIC32yield() is #define yield() — literally compiled out
Mega 2560 (your board)Calls the real yield() function

The library never calls wdt_reset() directly. During blocking socket work (socketSend waiting for TX buffer space, waiting for SEND_OK), it calls yield() as a hook so cooperative schedulers (ESP8266, etc.) can run.

But on AVR, yield() is also a no-op

Even when the real yield() is used, the AVR Arduino core defines it as empty:

static void __empty() {
  // Empty
}
void yield(void) __attribute__ ((weak, alias("__empty")));

So on your Mega: the library's "feeding" hook exists but does nothing for the watchdog. Nobody nulled out wdt_reset — the library never used it; it relied on yield(), which doesn't touch the WDT on AVR.

Where this matters for your cable-pull test

Blocking callCalls yield()?Feeds WDT on Mega?
socketSend() (inside write)Yes, in wait loopsNo — empty yield
client.connect()No — uses delay(1)No
client.flush()No — tight while loopNo
client.read() / available()NoNo

Optional workaround: override yield() globally

Because yield() is a weak symbol, you can provide your own in the sketch:

void yield() {
  wdt_reset();
}

That would feed the watchdog during every socketSend wait inside the library. It still wouldn't help client.connect() or client.flush() (they don't call yield()), which is why explicit wdt_reset() in your upload code is still needed.

Bottom line

  • Yes, the Ethernet library has a path where cooperative "feeding" is disabled via #define yield() — but not on your Mega.
  • On your Mega, yield() runs but is empty, so the library's internal waits do not feed the watchdog.
  • Cherry-picking fix/wdt_reset plus explicit wdt_reset() in your upload path (and optionally overriding yield()) is the right fix.
